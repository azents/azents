# Runtime Web routing correction requirements

## Phase 1: minimal robust routing

1. The Runner Web session channel must use the same operator-configured stable Runtime Control endpoint as the ordinary Runner Control connection.
2. A Runtime Control replica must not be able to redirect the Runner Web channel to a replica-specific or Pod-specific endpoint through a session offer.
3. Owner epoch, nonce, generation, authentication, and TLS validation behavior must remain unchanged.
4. Tests must prove that a Pod-specific address in an offer is not used as the Runner Web connection target.
5. The phase must remain a small, independently reviewable change based on current `main`.

## Phase 2: structural correction

1. Remove the redundant server-provided Runner connection address contract and its configuration after Phase 1 establishes Runner-owned routing.
2. Re-audit the merged Runtime Web HTTP and WebSocket path against the current Living Specs and implemented design.
3. Replace incorrect units rather than retaining obsolete address/owner coupling through compatibility branches.
4. Preserve existing authorization, generation fencing, bounded buffering, and no-replay behavior unless a verified defect requires correction.
5. Deliver Phase 2 as a stacked PR based on the Phase 1 branch.
