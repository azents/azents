# Provider Channel Participation Phase 4 — Discord Controls

## Phase Execution Plan

- Phase: `4 — Discord Provider-Native Controls`
- Branch/base: `feature/conversation-channel-participation-discord` → `feature/conversation-channel-participation-slack`
- PR boundary: Implement authenticated Discord-native setup and conversation settings controls, required command-set reconciliation and capability proof, signed component/options/modal scope, and direct parent-channel delivery while preserving the provider-neutral participation authority delivered in earlier phases.
- Inputs: Approved `conversation-260801` Requirements, ADR, and Design; the multi-phase implementation plan; Phase 1 schema/domain foundation; Phase 2 setup/ingress/parent Session contracts; and Phase 3 provider-neutral settings mutation interfaces and Slack parity expectations.
- Deliverables: Required Discord command-role list/create/update/delete reconciliation; persisted versioned role-to-command-ID capability map; command-role-aware admission; `Azents settings` and Conversation settings entry points; signed setup/parent/thread component and modal scope; setup location continuation and canonical settings mutations; connected Session presence settings action; parent delivery without thread provisioning; unchanged deterministic thread provisioning; focused fake-provider coverage.

- Interfaces: Discord activation reconciles required commands without bulk overwrite and commits a complete capability snapshot under existing Application/configuration fences; signed Ed25519 admission selects one exact command/component/options/modal handler from current command role, ID, name, and type; compact signed custom IDs or durable opaque state bind connection, Guild, parent/thread scope, route/default generation, setting or Binding generation, setup claim, principal, interaction, and page; provider I/O remains outside conversation/participation/database locks; provider outcomes cannot gate canonical mailbox admission, wake, or AgentRun.

- Absence verification: Repository search and activation tests prove the singular registration/capability authority is removed; parser/processor tests reject mismatched role/ID/name/type and unsupported custom IDs; reconciliation tests prove obsolete recognized Azents commands are removed and unrelated commands remain; delivery fakes prove parent Resources never call `ensure_thread` and thread Resources still do.
