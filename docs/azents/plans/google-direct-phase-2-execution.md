# Phase Execution Plan

- Phase: 2, direct SDK operations and authorized file handling.
- Branch/base: `feat/google-direct-execution` → `feat/google-direct-foundation` (`bd3e77ac4`); dependency PR [#2372](https://github.com/azents/azents/pull/2372) is open.
- PR boundary: Closed typed direct Gmail/Calendar/Drive operation families with bounded official SDK transport, current execution admission and canonical files; replacement of Google-only MCP execution/scanning. This intermediate stack is not a deployable cutover.
- Inputs: Approved [Design revision 1](../design/google-261021-direct-workspace-tools.md), [Requirements](../requirements/google-261021-direct-workspace-tools.md), accepted [ADR](../adr/google-261021-direct-workspace-tools.md), [implementation plan](google-direct-implementation-plan.md), phase 1 operation/request contracts and reviewed scope matrix.
- Deliverables: Per-call SDK lifetime and access-only authorization; typed operation inputs/results; all approved service families and compound prerequisite admissions; bounded file transfers/extraction; local FunctionTool projection reloaded each turn; current-grant/owner/client/config fences around renewal and effects.
- Non-goals: Live Google authentication/effects, operator deployment, new credential stores, arbitrary provider endpoints/method dispatch, operation approvals, selected-file ACLs, UI/Picker or management contract activation (phase 3), assembled product E2E fixture replacement (phase 4).
- Interfaces: Operation identity comes from the closed catalog, never model text. Invocation admits canonical execution owner and current Toolkit/personal access plus enabled service and actual scopes. Access-only credentials go to the supported SDK, with implicit refresh and operation retry disabled. Typed provider ingress tolerates unrelated provider fields without permitting arbitrary outgoing fields. File arguments use canonical file resources/Runner paths; outputs use existing authority-owned Artifact services. No external I/O inside repository transactions.
- Approved Design mechanisms: M1, M2, M3, M5 (actual Drive extent), M7, M8 (execution/scanner retirement), M10 (uncertain-operation handling), M13 (SDK/race/file tests).
- Authority references: google-261021/REQ-1 through REQ-8/REQ-10 as traced in Design; ADR-D1/D3/D4; Design sections 4/6/7/8/11/13; current Google Connection and File Exchange Storage Specs; supported SDK, layering, typed-ingress, cancellation and transaction conventions.
- Design delta: None.
- Removal obligations: Replace `GoogleServiceMcpToolkit`, Google endpoint discovery/snapshot consumption and MCP result extraction; remove Google regex schema/argument/result scanner and blanket binary rejection with obsolete scanner-only tests. Retain generic MCP machinery/other consumers. Task/ack management config, staged DTO/UI and migration activation remain phase 3. No dual-shape application decoder or fallback is introduced: until phase 3 replaces the config consumer, existing task membership supplies service composition only, never a direct-operation ceiling.
- Absence verification: Reference audit for GoogleServiceMcpToolkit/Google MCP hosts/google_screening and old remote discovery in production execution. Positive SDK/request-count/typed-validation/file/authorization tests replace deleted scanner tests. Legacy persisted state cleanup is implemented in phase 3 migration, and old fixture endpoints retire in phase 4.
