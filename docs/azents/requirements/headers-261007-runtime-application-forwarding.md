# Runtime Application Header Forwarding Requirements

## Problem and Primary Scenario

A user enables a temporary development service and logs in to the application.
The application's cookie must return to the application on later requests.
Removing the entire Cookie header breaks that scenario.

## Requirements

### REQ-1. Forward every application-owned header

Forward headers except fields consumed or regenerated by the proxy. Preserve
application cookies, Authorization, Origin, Referer, custom fields, and ordered
repeated values for HTTP and WebSocket requests and responses.

Acceptance: login cookie round-trip works; HTTP and WebSocket application
headers reach their peer; non-consumed values do not change or disappear.

### REQ-2. Retain proxy-owned transport and identity protection

Consume platform authentication cookies and connection-local transport/handshake
fields without removing unrelated application values.

Acceptance: platform secrets cannot enter the app or be replaced by its response;
Connection-nominated fields do not cross hops; WebSocket handshake remains valid;
all existing access, exposure, generation, and resource bounds remain enforced.

## Goals and Supporting Effects

- Application login and arbitrary application header contracts work.
- Correct hop-by-hop handling and platform credential isolation remain intact.

## Non-Goals and Fixed Constraints

- No anonymous access, authentication mode, migration, or new configuration.
- Retain numeric loopback routing and existing loopback redirect/cookie-domain
  adaptation. No change to platform-owned login or activation.
- No merge or operational deployment authority is included.

## Open Assumptions

Application-cookie names equal to platform-owned cookie names remain reserved.
Browser cookie rules and the application's own policies remain authoritative.

## Confirmation

Requester explicitly authorized implementation on 2026-10-07 and clarified:
forward everything unless the proxy must consume the field.
