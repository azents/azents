# Operational Schema Baseline Requirements

- Snapshot: `database-260915`
- Document reference: `database-260915/REQ`

## Problem

The consolidated fresh-database migration graph does not create the schema currently
used by the production Azents deployment. The deployed database and current
SQLAlchemy models agree, while a fresh upgrade reaches the same Alembic revision but
still requires additional autogenerated operations.

## Primary Context

### Primary System Outcome

Fresh Azents databases and the already-current production database must represent
the same current RDB schema, and continuous integration must reject future
SQLAlchemy metadata drift.

## Supporting Scenarios or Effects

- Existing production databases already recorded at the current revision continue
  starting without schema writes.
- Historical transition-only migrations are not required for a new empty database.
- Migration verification detects schema/model drift before a change can merge.

## Goals

- Make an empty supported PostgreSQL database converge to the production schema.
- Preserve the revision identity already recorded by the production deployment.
- Detect new Alembic upgrade operations in CI.
- Keep required deterministic singleton seed state on fresh databases.

## Non-Goals

- Apply migrations or mutate data in the production cluster as part of this change.
- Preserve downgrade paths into removed intermediate schemas.
- Preserve transition tests whose source and target revisions are removed.
- Copy production application data into repository fixtures or migrations.

## Requirements

### REQ-1. Production-equivalent fresh schema

An empty supported PostgreSQL database upgraded to the repository head must have the
same public schema as the current production database and current SQLAlchemy
metadata.

**Acceptance criteria**

- Fresh `alembic upgrade head` succeeds.
- `alembic check` reports no new upgrade operations on the fresh database.
- The normalized public-schema catalog matches a read-only production schema
  snapshot taken from the deployment running the same application revision.

### REQ-2. Existing deployment compatibility

The production database already recorded at revision `097a97177350` must remain
current without executing DDL.

**Acceptance criteria**

- The repository head retains revision ID `097a97177350`.
- The consolidated graph contains exactly one head and no ancestor revision.
- Startup revision checks continue to observe the production database as current.

### REQ-3. Fresh-database seed state

Fresh databases must retain deterministic singleton rows required by runtime
services.

**Acceptance criteria**

- File lifecycle settings contain the current default singleton.
- Runtime connection generation cutover contains the current singleton.
- Runtime Web authentication configuration contains the current singleton.

### REQ-4. Continuous schema drift detection

Python migration CI must fail when SQLAlchemy metadata requires operations beyond
the checked-in migration head.

**Acceptance criteria**

- Migration CI executes an Alembic model-definition-versus-DDL check against
  PostgreSQL after upgrading to head.
- The check passes for the consolidated baseline.

## Fixed Constraints

- The production deployment inspected on 2026-09-15 runs application revision
  `8da2953aebb6257861f8ab2ea6576bd7021ab9df`.
- The production database is at revision `097a97177350`.
- Production inspection is read-only; this repository change does not apply DDL to
  the live database.

## Open Assumptions

- Every supported deployed database has already reached revision `097a97177350`.
