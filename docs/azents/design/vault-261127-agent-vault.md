# Agent Vault Design

- Snapshot: `vault-261127`; document reference: `vault-261127/DESIGN`.
- Authority: [vault-261127/REQ](../requirements/vault-261127-agent-vault.md) and [vault-261127/ADR](../adr/vault-261127-agent-vault.md).
- This design describes the proposed implementation, not current behavior. Approval and implementation are separate.

## Current system and gaps

- [Runtime environment settings](../spec/flow/agent-runtime-persistence.md#per-agent-runtime-environment-variables) manage a separate encrypted mapping automatically supplied to commands. They cannot satisfy scoped, explicit use or a metadata-only per-entry Vault.
- [Session Browser](../spec/flow/session-browser.md#delegated-confidential-field-input) already accepts encrypted fill, but the documented delegation workflow relies on a shell process with an environment value. Vault fill needs an application-side binding to the authenticated Runner recipient.
- [Runtime Control](../spec/flow/agent-runtime-control.md#coordination-store) admits and fences operations. In ordinary operations the process environment is carried in the start request and file bytes in read replies. Hiding tool output alone would not protect Vault transport.
- [Chat resync](../spec/flow/chat-session-resync.md) projects append-only history; it does not update a detached page just because a later event arrived. [Mailbox admission](../spec/execution/mailbox.md) carries wake intent, but a Vault request is not a waiting Run, human composer input, or Channel Work.
- [External Channel delivery](../spec/flow/external-channel-delivery.md) owns provider I/O and best-effort effects, but Channel Work targets its own binding. A Vault request needs a distinct source Session and an explicitly authorized delivery target.

## Ownership, storage, and settings (M1–M2, M11–M12)

PostgreSQL owns the Agent's entries and the Session's requests. Transport, tooling, UI and provider projections do not grant ownership. Workspace and Agent identity come from authenticated scope and stored relations, not from a requester-supplied Agent override.

| Record | Owner and identity | Stored fields and invariants |
| --- | --- | --- |
| Vault entry | Exact Agent; database-unique `(agent_id, name)` | Validated name, encrypted value, informational contributor label, timestamps. Use exact case-sensitive names. Settings metadata query does not select or decrypt ciphertext. Agent removal deletes entries; Session archive or purge does not. |
| Vault request | Original Session and its Agent; opaque request ID | Ordered distinct entry names and display labels, purpose, creation instant, deadline, status, terminal timestamp, and immutable transcript placement reference. No submitted values. Own the request with the Session lifecycle; verify the Agent through that relationship. |
| Optional delivery projection | Part of the request, not a binding or a second owner | Exact admitted binding, route and provider target; claim and outcome evidence for one create and one terminal edit. A confirmed receipt includes provider installation/author evidence and the actual channel and message identity. No provider credentials, value, form fields' submitted contents, or persisted full link needed. |

Add a Vault section in the exact Agent's settings using the existing Workspace Owner or exact-Agent administrator predicate, not the more permissive Runtime settings metadata policy. List names and contributor labels, create a name/value, replace the value for an existing name, and delete by name; no API returns a value and the replacement input starts empty. Use authenticated Agent settings API routes scoped to the Agent; expose separate typed metadata, create, replacement and deletion contracts. Create conflicts on an existing name; replace or delete must not implicitly create a missing entry. Resolve and recheck active Agent and current management authority on each mutation. Contributor provenance may reflect the current human or the registering Agent; it grants no rights.

Encrypt at the application boundary with the existing `CredentialCipher` and `AZ_CREDENTIAL_ENCRYPTION_KEY` before writes. Use a dedicated repository/service; do not migrate, merge or auto-import the existing Runtime environment. Batch submission upserts only the specifically disclosed request names under manager authority. Show the destination names and that submission sets their values; no prior value is read for the form. All batch writes are atomic. Enforce uniqueness in PostgreSQL and serialize conflicting writes under the existing active-Agent write guard. A file registration is create-only; a name collision cannot overwrite. Selecting entries for use reads and decrypts only the relevant rows. A missing member of a CLI map aborts the whole call before dispatch. Replacement or deletion governs subsequent reads; it does not retract an already admitted use.

## Explicit use and confidential transport (M3–M6, M12)

### Interfaces and recipients

| Surface | Accepted identifying inputs | Value boundary |
| --- | --- | --- |
| `exec_command` | Existing fields plus optional `vault_env`: environment-variable name to Agent entry name | Application reads selected entries after checking execution and Runtime authority. Runner admits and opens a sealed map only before building the selected process's environment. Output and process lifecycle stay ordinary. |
| `browser_act` | Existing fill target plus optional `vault_entry`, exactly one of `text`, `encrypted_text`, `vault_entry` for fill; reject `vault_entry` on other actions | Application seals the selected value for the exact admitted Browser Runner and dispatches existing `encrypted_text`. Browser target and observation checks still apply and decryption stays at fill. |
| `vault_register_file` | Accessible Runtime path and destination entry name | Runtime reads one bounded file and seals it for the originating application. Application returns entry metadata or a fixed error, never contents. No human launch or settings identity is required, including for shared Agents. |

Do not take a separate Agent identifier from these tools. Derive owning Agent, Session, Runtime and admission authority from current execution. For CLI, use the ordinary command schema and process rules when `vault_env` is omitted or empty. Validate normal environment variable names and reject Runtime-/Runner-owned keys, including the Browser input public-key variable. Build the usual effective environment for a confidential command then apply nominated ordinary values only to that launch, so a valid explicit assignment is not silently shadowed by an inherited or general environment setting. Reject invalid input, including values unrepresentable as process environment strings, before starting any process. No shared environment mutation, temp file, inline shell substitution, or secret lookup result. Preserve output, cwd, resource quotas, fire-and-forget and managed-process semantics.

Use authenticated Runner registration to associate distinct Browser and CLI public recipient keys and supported capability with the admitted generation. Keys originate in the Runner process. Only existing Browser public-key exposure to child processes is retained; no transport private key or new general secret material is inherited. A replacement process creates new recipient keys. The application generates a fresh file-reply recipient for each operation; only its public key travels in the request, and the private key is released on completion, failure or timeout. The application storage key is never a transport key. A missing, unsupported or stale recipient fails closed. Redis is not a key authority independent of authenticated registration and existing Control authorization; protection covers ordinary stream contents and retention, not a compromised endpoint or authorized Control plane.

### Runtime Control contract

- Extend the typed Runner/Control protocol with a confidential process-start request and confidential file-read request/reply, separate from ordinary plaintext payloads. Admit, authorize, assign the operation identity, choose the recipient for the exact generation, bind and seal, then append with the atomic current-generation fence. No plaintext fields enter a serializable envelope, even if append is rejected. Do not let an already sealed operation auto-rebind to a different generation. Existing transport registration, acknowledgement and event cursor semantics remain in force.
- Encode the confidential body with a closed context containing direction, operation kind, Runtime, admitted Runner generation, owning Session, operation identity and deadline. Validate the decrypted context against the admitted operation before an effect or storage write. Apply cryptographic bounds before decoding and reject malformed, swapped, stale and incomplete bodies. The authenticated dispatch and reply channel establishes peer authority; a public key or a decryptable envelope alone is not sender authority. Browser continues to use its existing encrypted fill envelope and distinct recipient, with exact target and generation fencing.
- Retain protected bodies as ciphertext under existing stream policy on both Redis and in-memory implementations. No private key, plaintext, secret hash, replay token carrying plaintext, or alternate body store. CLI/file support is additive and capability-gated; no new protocol negotiation mode, transport service or object copy. Expiry, cancellation and an unknown append/start outcome use existing operation settlement. Never retry an uncertain CLI start. Observe an uncertain Browser fill before any repeat. A lost file recipient or unverified terminal result cannot produce a write.
- Resolve a file path in the current Runner's Runtime namespace using the existing filesystem visibility rules. Open a readable regular file without blocking on special files, validate the opened descriptor, and read up to the permitted bound plus one byte. Require a complete bounded UTF-8 value without trimming, truncating, or rewriting it. Validate aggregate and per-field limits at each ingress against the applicable transport and consumer limits; Browser fill retains its current 4096 UTF-8 byte limit and rejects a value it cannot accept without narrowing the ordinary CLI contract. Reject unreadable, malformed, oversized or incomplete input with a fixed error; no new file is created and the original is not removed. Do not include content, encoding error snippets, or raw environment errors in diagnostics. Recheck the requesting execution and owning Agent at the application write fence after the reply, before creating the entry.

## Request, card and inbox (M7–M9, M11–M12)

### Request creation and display

An execution calls `vault_request` with a bounded purpose, a nonempty ordered list of distinct named fields and labels, and optionally one explicit Discord or Slack channel reference. The caller supplies no values, expiration override, submitter or alternate Agent. Use the exact originating Session even for a child execution. Precheck Session eligibility and the explicit destination; do not silently convert a rejected channel target to some other destination. Commit a value-free request and a standalone transcript event anchoring its chronological position together. The tool returns the request ID and acknowledgement of creation, not human values and not an assertion that an asynchronous provider post succeeded. Run execution continues normally.

The history item and live append use the existing history stream and session identity. Do not lower this UI anchor into a model-visible chat turn or mark it as a human message. Embed only identity and value-free display metadata in the projection. Read current status from the request, not from a permanently captured event body. Batch-projection on history reads, current request reads for visible cards, and value-free invalidation on the existing session channel let live, paged and detached timelines refresh the same event identity. Re-read on reconnect; while an open card is displayed, refresh it at the deadline and use bounded revalidation for a missed status signal. No status mutation of immutable history and no second cursor/ordering stream. Preserve the anchor against displaced-event collection while the request row is open, even under zero-day retention; after settlement, ordinary compaction history retention applies. A still-mounted card with a missing anchor after terminal cleanup can resolve its request status without recreating an event or reviving an action.

The card displays purpose, field labels and status; it does not open a dialog on delivery or change composer focus. A click, or one explicit `vaultRequest` query intent on the canonical Session route, opens the same dialog. Preserve that relative path and query through sign-in, including stale sign-in during Workspace resolution. Resolve only the exact Workspace, Agent, Session and request tuple. Check current Workspace membership and Team or exact User Session owner access first, then separately check Vault management. Link possession and channel membership grant neither; keep private, mismatched and unauthorized lookup not-found-safe. Once handled, consume the URL open intent without changing the selected Session or restarting it. The dialog shows the requesting Agent and empty input fields. Keep values in local form state and the authenticated submit body only; clearing, dismissing or unmounting the dialog never writes them to draft, history, telemetry, storage or URL. Dismissing a dialog does not close the request. A terminal or inaccessible request exposes no input action.

### Access and settlement

The typed request status and submit contracts are scoped to the exact Session and opaque request ID, not a separate public form page. The chat status projection is value-free; only the designated manager predicate together with exact conversation access allows an input dialog or submit. The submit body contains exactly one value per declared field, rejecting omissions, duplicates, extra names and malformed values without echo. Use existing authenticated mutation protections. Public settings and form responses are non-cacheable where relevant and safe to log only through redacted outcomes.

| Stored state | Incoming action and conditions | Result |
| --- | --- | --- |
| Absent | Eligible execution creates request | `OPEN`, durable deadline = database creation instant plus 24 elapsed hours. |
| `OPEN` | Authorized submit under current Agent/Session/request fences with elapsed database time strictly before deadline | `SUBMITTED`; write all entries, terminal status and one wake-capable mailbox input in the same transaction. |
| `OPEN` | Elapsed database time is at or later than deadline | Effectively expired for every open/submit decision; scheduler persists `EXPIRED`. Any submit contender past deadline is rejected without entry or inbox writes. |
| `SUBMITTED` or `EXPIRED` | Duplicate, late submit, retry, or provider result | No secret mutation, inbox input or change to terminal status. |

Acquire the current active Agent guard and applicable root and exact Session lifecycle locks in canonical order before locking the request. Under that fence revalidate access, no outstanding operator stop, exact Session ownership, and deadline with elapsed database time after lock waits. Do not use transaction-start time. Take the serialized accept decision immediately before admitting the batch and enforce a bounded transaction. The same request lock and status predicate serialize the scheduler and submissions. A policy or mailbox failure rolls back all success effects, with no provider I/O or broker wake inside the transaction. Duplicate after mailbox consumption still observes terminal request state. Use a typed, value-free completion payload with request identity, not the form body or a forged user message; lower only the needed completion fact into execution. Compose the existing wake-capable admission in the transaction, including its durable running transition. Active Sessions continue without restart; an idle Session is woken. Post the normal routing-only wake after commit. A missed wake leaves a durable input; current stale-running recovery can re-signal eligible Sessions, not promise immediate recovery. Never retarget to a parent Session. Expiry and archive do not enqueue completion or wake.

Archive and Agent retirement fence new writes and wake through existing authorities. No separate cancellation mode is created. Archive blocks access and submission without extending the original deadline; restore under the existing lifecycle may admit a still-open, unexpired request but does not reopen any terminal request. The expiry pass may settle a still-retained request while its source is archived. Session purge removes request rows and delivery evidence through the normal Session resource catalog; Agent deletion removes Agent-owned entries through its registry and relies on the Session lifecycle for original Session resources. The archived Session's retention job is never blocked by provider delivery work.

## Exact channel publication and terminal edits (M10–M11)

Resolve the specified provider and exact channel to one connected, routable binding for the same Workspace and Agent. Fail closed on absent, ambiguous, disconnected or revoked targets. Match actual channel or thread identity as specified, not the source conversation, a parent-channel inference, or a mutated label. Store immutable routing evidence that suffices to verify the same installation/author and exact target later. Recheck live connection, route and provider access at dispatch. This is a read of delivery authority, not permission to mutate Channel Work or a second grant to submit.

Reuse the existing scheduler/job execution for bounded passes on the request rows: find due expiry, eligible unclaimed initial posts, and eligible unclaimed terminal edits. Persist claim/disposition on the request row with predicates; no network under DB locks. Use database time, a batch limit and existing job deadlines. In-memory worker state is not authority. Do not send a newly claimed initial post if the request is no longer open or its source is no longer eligible. The exact destination receives one initial message with its Azents link. Only a confirmed receipt supplies the exact edit address: Discord actual channel + message ID with guild/installation evidence; Slack actual channel + timestamp with tenant/installation evidence. Preserve that address even if completion races with the post's reply. Never replay an ambiguous create, discover another message to edit, or fall back. A crash after a claim can leave a send unattempted or unknown; no fabricated delivery success.

For a confirmed receipt and terminal request, claim one best-effort edit and replace all link-bearing content, components or blocks on that same message with the link-free completion or expiry status. No separate durable retry workflow, repeated edit, or detached cleanup record. Unclaimed eligible work survives a scheduler restart. A provider failure, revoked target, unknown create, concurrent purge or crash after an edit claim can leave a visible dead link. Server-side invalidation is immediate and independent. Source inactivity alone is not alternate delivery authority: a terminal edit is only eligible for a retained request and an exact destination that still passes D5; revoked authority cannot be reacquired via this feature. No provider result can reopen a request, undo a committed submission or send a wake to the destination.

## Migration, rollout, and operations

- Use additive database tables, bounded due-work indexes and lifecycle catalog entries. Validate Session purge manifests and Agent deletion against new relations with preexisting archived Sessions and fenced jobs; do not enable writes until catalog coverage is present. No data migration, environment rename, credential re-encryption or backfill is needed. Follow existing Public API client and protobuf generation workflows on implementation; no separate legacy Vault paths or mode.
- Roll out database/catalog support before exposing writers; deploy Control and compatible Runners before advertising Vault-backed execution in participating deployments. Mixed-version recipients must not receive a confidential request as ordinary CLI, file or literal Browser input. Compatibility failures are explicit, and ordinary callers continue. For rollback, quiesce Vault writers and provider dispatch, stop exposing Vault interfaces, preserve additive tables and the matching credential key, and verify lifecycle coverage before running a revision that cannot purge Vault data. Do not drop user entries as an application rollback shortcut. Outstanding links cannot submit while the feature is unavailable or after their original deadline; do not extend deadlines on re-enable. Use the existing deployment rollback process, not a public feature toggle.
- Keep backups paired with the corresponding existing credential key through separate secret custody. Shared-key exposure affects all data encrypted by it. Key replacement requires coordinated re-encryption before switching, not creation of an unsupported automatic rotation mode. Retained ciphertext is vulnerable if the matching transport private key is also obtained. Non-echoing behavior is the verification boundary; ordinary stdout, stderr, pages and intentionally present Runtime files remain as-is.
- Use bounded English reason codes and counts for admission, not-found/conflict, expiry, completion admission, unsupported or stale recipient, and provider unknown/failure/revocation. Emit only necessary routing IDs and timing evidence. Do not trace request bodies, plaintext or encrypted bodies through model/error paths, secret variable assignments, paths containing raw exception values, full URLs, private keys or value-derived hashes. Sanitize validation and nested exception paths at ingress, publisher, task and Runner boundaries; use normal logging integration. Alerting and diagnosis do not add automated resend authority.

## Test Strategy

Use E2E at actual product boundaries for the core journeys; put scheduling, race and wire permutations in deterministic integration tests instead of duplicating end-to-end combinations.

| Primary E2E journey | Evidence | Requirement/mechanism |
| --- | --- | --- |
| One management and consumption journey on a shared Agent | Separate settings section and metadata-only response; another Agent cannot consume the entry; synthetic scoped CLI value, missing entry abort, next command has no injected Vault value; register a readable Runtime file without a human manager and consume its value; fill a synthetic password input without shell | REQ-1–REQ-3, REQ-5; M1–M6, M12 |
| One Main Web request journey | Actual nonblocking request yields a standalone card without focus change; explicit dialog opens for authorized actor; account/password submission updates the same card and resumes an idle original Session on value-free input. Reopen history/reconnect and verify it remains closed. A denied actor gets no input surface | REQ-4–REQ-5; M7–M9, M11–M12 |
| Exact Discord/Slack provider journey, parameterized where fixture permits | One link-bearing post at configured alternate destination; sign-in round-trip opens the original Session and shared dialog; completion or fixture-driven timeout updates the same known message without link. Across the two providers exercise success and visitor-free expiry; the denied link must not write | REQ-4–REQ-5; M7–M12 |

Extend the existing required E2E suites for Runtime environment, Browser confidential input, Discord journeys and Slack fake-provider flows. Use testenv only for fixture services, deterministic expiry, provisioned runner and provider prerequisites, and diagnostics; passing testenv spot checks are not substitutes for web/API/Runner journeys. Use disposable Workspaces with Owner, exact-Agent administrator, ordinary member and other User Session owner; two Agents can share an entry name without sharing data. Seed app and provider credentials and capture only safe fixture/prerequisite descriptors (configured versus fake, image/build ID and capabilities, connected channel kind, isolated workspace). Synthetic high-entropy markers and non-echo consumers yield boolean/exit-code evidence, not credential text or raw authenticated screenshots. Use deadline fixtures rather than waiting 24 hours, and barrier or authoritative-state synchronization for concurrency.

Deterministic checks: name uniqueness and batch atomicity; submit vs duplicate after inbox consume, expiry after lock wait, stop, archive, retirement and purge; active versus idle wake, post-commit signal loss, no expired wake; detached and two-tab refresh, zero-day compaction and stale login; exact destination and creation ambiguity or reply arriving after expiry, edit failure and authority revocation; typed protobuf and raw Redis/in-memory record inspection, cancellation, generation replacement, old Runner, sealed cross-operation mismatch, invalid file type/encoding/limit, unavailable recipient, and ordinary output compatibility. Check fixture logs, feature diagnostics, transcript, settings bodies, model requests, and Vault request/reply streams for absence of the synthetic plaintext and private key material; the positive consumer assertions must also pass.

Run required isolated E2E and narrower checks in ordinary CI with synthetic values and deterministic provider mocks. Missing a required compatible Runner, seed or fake-provider prerequisite is a setup failure, not a skip. Optional live Discord/Slack smoke may skip only when live credentials or authorized test channels were not provisioned; if configured, unexpected auth or delivery failure is a failure. Record case IDs, release/build and fixture descriptors, sanitized outcomes, and whether live optional coverage ran. Do not use production values. No implementation tests have been run for this design.
