# Agent Vault ADR

- Snapshot: `vault-261127`
- Document reference: `vault-261127/ADR`
- Requirements: [vault-261127/REQ](../requirements/vault-261127-agent-vault.md)
- Mode: Collaborative; the requester owns open material decisions.

## Current architecture and fixed boundaries

- Agent Runtime environment values are kept as one encrypted Agent mapping and merged with other environment sources for ordinary command launch. Vault entries have different use semantics, so the existing environment contract and stored values remain unchanged. Reusing the encryption facility does not imply reusing the environment dataset or loader. See [Runtime persistence](../spec/flow/agent-runtime-persistence.md#per-agent-runtime-environment-variables) and [credential encryption](../../../python/apps/azents/src/azents/core/crypto.py).
- Session Browser already admits the live target and supports confidential `encrypted_text` input. The current source path assumes a Runtime environment value. Vault Browser input does not use that shell step. The browser and command paths retain their existing authorization and execution fences. See [Session Browser](../spec/flow/session-browser.md#delegated-confidential-field-input) and [Runtime execution](../spec/tools/runtime-execution.md).
- The existing Session mailbox persists scheduling intent with input admission and uses a routing-only notification after commit. A normal queue-only message would not wake an idle Session. The Vault success signal must use the wake-capable path without asserting a separate Run pause/resume state or embedding submitted values. See [Session mailbox](../spec/execution/mailbox.md).
- Channel Work acts on a current binding. Its input-wait state and destination selection cannot be used as a substitute for an independent Vault request, its exact authorized delivery channel, or completion into the original Session. Provider delivery and message-mutation capabilities are reuse candidates. Conversation access and Vault management are checked independently for channel-link visitors. See [External Channel delivery](../spec/flow/external-channel-delivery.md) and [Conversation](../spec/domain/conversation.md).

## First decision brief: persistence and key boundary

**Question:** How should named Vault entries be stored and encrypted separately from the auto-injected environment dataset?

- **A. Separate encrypted record per Agent and entry.** Store authorization-scoped metadata separately from ciphertext, with database-enforced name uniqueness within the owning Agent. A use can select and decrypt only the requested entries. A form can write several entries in one database transaction. Costs include a new owned relation, migration, explicit Agent deletion handling, and review of locking for batch operations.
- **B. Separate encrypted map per Agent.** Keep one additional encrypted Vault map separate from existing Runtime settings. Agent-level writes can reuse the current merge-and-lock pattern, but named lookup and entry metadata listing require opening the map unless another metadata projection is added. Edits across that Agent serialize on one map and replace it as a unit.

**Recommendation:** A, using the existing application credential encryption facility for initial deployment unless a separate key or an independently operated secret store is required. This avoids a new infrastructure prerequisite and allows metadata-only reads and narrower decryption. Reusing the current key shares its compromise and rotation boundary; a distinct key reduces that coupling at the cost of another configured and recoverable key lifecycle. Neither option changes or migrates existing Runtime environment values.

## D1. Store separate encrypted records per Agent and entry

- Status: Accepted on 2026-11-27.
- Requirements: [vault-261127/REQ-1](../requirements/vault-261127-agent-vault.md#req-1-manage-agent-owned-entries), [vault-261127/REQ-2](../requirements/vault-261127-agent-vault.md#req-2-explicitly-use-entries-in-a-tool-call), and [vault-261127/REQ-5](../requirements/vault-261127-agent-vault.md#req-5-keep-plaintext-out-of-normal-product-records).
- Decision: Store each named Vault entry in an independent, Agent-owned encrypted record. Keep name and contributor metadata readable under the appropriate authorization without opening ciphertext. Scope the entry name to its owning Agent and decrypt only the values needed for the operation.
- Rationale: Per-entry storage matches metadata-only listing and explicit use by name. An Agent-level encrypted map would require opening the entire map for ordinary use and would serialize independent entry changes as map replacements.
- Consequences: The design must address the new Agent-owned relation, batch writes and conflicts, and Agent deletion. Existing Runtime environment values and loading behavior remain unchanged. The encryption key boundary is a separate open decision.

## Decision brief: encryption key boundary

The current deployment supplies `AZ_CREDENTIAL_ENCRYPTION_KEY` to the application. The existing `CredentialCipher` uses a single Fernet key; replacing the configured key alone does not re-encrypt stored values. The selected per-entry records do not determine which deployment key encrypts them.

- **A. Reuse the existing deployment credential key.** Use the current application encryption facility without adding a deployment secret or changing existing ciphertext. Operators preserve one key for backup and restore. Disclosure of that key affects both Vault ciphertext and the other credentials encrypted with it. Future key replacement must account for both sets of ciphertext.
- **B. Provision an independent Vault encryption key.** Use the same established encryption primitive but a separately provisioned key, with no silent fallback to the existing key. Disclosure of one key alone does not decrypt records encrypted with the other. Opening both from a compromised application process remains possible. Deployment, backup, restore, and planned replacement must manage the second key.

**Recommendation (pending):** A for the first release, unless independent key custody or replacement is a deployment requirement. This retains existing deployment and restore prerequisites. Neither option adds automatic rotation or key versioning; the design must state the selected key's backup and replacement constraints.

## D2. Reuse the existing deployment credential encryption key

- Status: Accepted on 2026-11-27.
- Requirements: [vault-261127/REQ-1](../requirements/vault-261127-agent-vault.md#req-1-manage-agent-owned-entries), [vault-261127/REQ-5](../requirements/vault-261127-agent-vault.md#req-5-keep-plaintext-out-of-normal-product-records).
- Decision: Encrypt Vault entry values using the existing application `CredentialCipher` and `AZ_CREDENTIAL_ENCRYPTION_KEY`. Keep the key at the application encryption boundary, not in model context or the Agent Runtime. No new deployment key, key versioning, or automatic rotation is introduced by this decision.
- Rationale: Reuse the existing deployment and recovery setup while keeping Vault records and access paths separate. An independent key would narrow the impact of exposure of one key but introduce separate provisioning and recovery obligations.
- Consequences: Preserve the matching key with backups. Exposure of the shared key affects Vault and other ciphertext protected by that key. Replacing it requires a coordinated re-encryption plan; swapping the configuration alone cannot read or re-encrypt existing ciphertext. Existing encrypted values and deployment configuration are unchanged.

## Decision brief: consuming tool interfaces

The current `exec_command` implementation supplies a process-specific environment to the Runner after Runtime admission; its model-facing input does not accept Vault references. `browser_act` already validates the Session and live browser target and supports literal input and the existing confidential ciphertext input. Its current confidential workflow reads a Runtime environment value in a separate shell command, which is not the approved Vault Browser flow. A Vault reference is an identifier, not authority to access another Agent's data or a substitute for either tool's admission checks.

- **A. Extend the existing consuming tools.** Add an optional, structured map from environment variable names to Vault entry names to `exec_command`, and an explicit Vault entry reference as another mutually exclusive source for `browser_act` fill. Keep existing inputs and behavior for calls that do not request Vault entries. Resolve only explicitly requested entries after checking the applicable authority, outside model-visible tool inputs and before dispatch. This keeps one familiar command interface and one browser action interface, at the cost of extending their contracts and carefully separating confidential failure handling from ordinary diagnostics.
- **B. Add separate Vault-aware command and browser tools.** Use the same execution services and controls but expose distinct model-facing calls for commands and browser fills that use Vault. Existing tool schemas remain unchanged, and the sensitive path is explicit in tool discovery. This adds tool selection overhead and requires shared internal admission and recovery code so the two interfaces do not diverge.

**Recommendation (pending):** A. Preserve the existing command and browser admission boundaries, with a structured reference rather than templating values into shell text or resolving a model-supplied placeholder in arbitrary text. Neither option returns plaintext to the model or requires a separate lookup call. File registration remains a separate operation from consuming a value; the existing model-visible file-read output is not an intake interface. The exact internal Runner transport, sanitized errors, and file-import byte handling still require feasibility checks; this decision would select the consuming interface, not authorize plaintext in ordinary logs or browser command records.

## D3. Extend the existing command and browser tools

- Status: Accepted on 2026-11-27.
- Requirements: [vault-261127/REQ-2](../requirements/vault-261127-agent-vault.md#req-2-explicitly-use-entries-in-a-tool-call), [vault-261127/REQ-3](../requirements/vault-261127-agent-vault.md#req-3-register-a-value-from-an-agent-runtime-file), and [vault-261127/REQ-5](../requirements/vault-261127-agent-vault.md#req-5-keep-plaintext-out-of-normal-product-records).
- Decision: Extend `exec_command` with an optional structured environment-variable-to-Vault-entry mapping. Extend `browser_act` fill with an explicit Vault entry reference mutually exclusive with literal text and the existing ciphertext input. Both tools retain their existing execution and target admission checks. References are resolved against the executing Agent, outside the model-visible arguments and results. Calls without Vault references retain their existing behavior. File intake is a separate operation and does not return file contents.
- Rationale: The familiar consuming tools already express the target operation. Separate Vault-aware variants would duplicate a model-facing choice without altering the authorized effect.
- Consequences: Extend the two model-facing contracts and cover incompatible input combinations, missing entries, and plaintext-free failure handling. This does not determine the internal Runner transport or the treatment of environment-name conflicts.

## Decision brief: successful submission and Session inbox admission

A successful form submission changes the Vault entries and closes the request. It must also leave a durable, value-free completion input for the requesting Session. Broker wake-ups carry routing identity, not input data, and are sent after commit. The existing [mailbox admission](../../../python/apps/azents/src/azents/repos/mailbox/admission.py) can compose a database write with a wake-capable input and the Session's durable running transition. Worker [stuck Session recovery](../../../python/apps/azents/src/azents/worker/session/recovery.py) can re-signal eligible stale running Sessions; that is a recovery path, not an immediate delivery guarantee.

- **A. Admit completion in the submit transaction.** In PostgreSQL, commit the encrypted writes, submitted request state, and one wake-capable mailbox item together. Serialize success, duplicate submission, and expiration against the request state so only the winning submission creates a completion input, even after the mailbox item has been consumed. Emit the existing routing wake after commit. If the signal is missed, the input is already durable and eligible Session recovery can re-signal it. This avoids a separate delivery queue, but requires coordinating the Vault and mailbox writes and validating the target Session's lifecycle in the same operation.
- **B. Commit the submission and a durable delivery receipt, then admit the inbox item separately.** A retryable dispatcher admits the completion and wakes the target Session after the Vault write. This decouples submission from mailbox admission and permits dedicated retry timing, but introduces a second durable state machine and requires deduplication across dispatch retries, including after mailbox promotion. The form can show completion before a notice is admitted.

**Recommendation (pending):** A. Both writes are in PostgreSQL, and the approved workflow needs normal Session inbox and wake behavior rather than a second execution workflow. Keep provider message updates outside this transaction; a Slack or Discord edit failure must not reopen a completed request. The design still needs evidence for active and idle Session delivery, a missed broker signal, and exact lifecycle fences. This brief does not decide whether cancellation or expiration itself wakes the Session.

## D4. Commit successful submission and the Session inbox input together

- Status: Accepted on 2026-11-27.
- Requirements: [vault-261127/REQ-4](../requirements/vault-261127-agent-vault.md#req-4-collect-multiple-values-in-azents-and-close-the-request) and [vault-261127/REQ-5](../requirements/vault-261127-agent-vault.md#req-5-keep-plaintext-out-of-normal-product-records).
- Decision: In one PostgreSQL transaction, save the encrypted entries, close the request as submitted, and admit a single value-free completion item with wake intent for the requesting Session. Serialize completion with expiry and other submissions using the request's persisted status; repeated submission does not save a second time or enqueue a second item. After commit, send the existing routing-only Session wake. Provider status updates are outside this transaction.
- Rationale: The submission and mailbox share a database boundary. Keeping both writes together removes the durable gap between saved values and an admitted completion notice without a separate admission dispatcher.
- Consequences: Verify the current Session admission and recovery boundaries, including failure to admit, missed wake for eligible Sessions, and active and idle consumption. A provider update failure cannot make the form submittable again. No new pause/resume state or cancellation/expiration wake policy is selected.

## Decision brief: authority to post Vault request links

Existing Channel Work publishes to its own connected binding after validating the route, connection, and provider target. A Vault request can explicitly name a channel different from its source conversation, including from a web Session with no Channel Work. The destination's provider permission to post is necessary, but does not by itself establish which Agent Azents authorizes to post there. A destination binding, if used, is evidence for delivery only; it does not own the Vault request or receive its completion input.

- **A. Use channels already connected to the requesting Agent.** Resolve the supplied channel ID to an exact active provider target with a connected binding and routable Agent association in the same Workspace. The request can select another such channel or originate from web chat. Recheck the route, connection, and provider permission at dispatch; reject absent, ambiguous, or revoked destinations without choosing a fallback. This reuses the existing configuration and lifecycle. An unconnected channel must first be connected to the Agent.
- **B. Add separately managed Vault notification destinations.** Give an administrator a distinct way to authorize an exact channel on an eligible provider connection, without binding that channel for Agent conversations. This supports notification-only channels but adds a new authorization surface, edit/revoke lifecycle, and operator setup. An arbitrary provider-visible channel ID is not sufficient in either option.

**Recommendation (pending):** A for the first release, unless posting to an unconnected, notification-only channel is required. Store the exact provider message identity needed for status updates rather than re-resolving the destination from the conversation. Recheck authority for a provider update and never fall back to another channel or alter the source Session. Link invalidation remains authoritative even when message editing is unavailable. The cleanup retry policy is not selected by this brief.

## D5. Post links only to channels already connected to the requesting Agent

- Status: Accepted on 2026-11-27.
- Requirements: [vault-261127/REQ-4](../requirements/vault-261127-agent-vault.md#req-4-collect-multiple-values-in-azents-and-close-the-request).
- Decision: The specified Discord or Slack destination must resolve to an exact, connected target for the requesting Agent in its Workspace. Apply the existing route, connection, and provider authority at dispatch. Reject unavailable, ambiguous, or revoked destinations without substituting another target. Do not add notification-only destination configuration.
- Rationale: Existing connected-channel configuration is the authority for where the Agent can send a request. Independent notification destinations are not needed for this scope.
- Consequences: The destination provides delivery authority only. It does not change the requesting Session, the destination of its completion input, or access to the Azents input dialog. Provider message cleanup remains a separate design concern.

## Decision brief: confidential Vault delivery to Browser

The current [Browser confidential fill](../spec/flow/session-browser.md#delegated-confidential-field-input) already accepts ciphertext for the current Runner process. The Runner decrypts after target admission and maps confidential fill failures to value-free errors. Its public key is currently supplied to Runtime command processes; the inspected contract does not expose an application-side key lookup. The existing shell helper is not an option for Vault Browser fill, which must bypass the shell.

- **A. Reuse the Runner's encrypted Browser fill.** Expose the recipient public key to the trusted application for the exact admitted Runner generation. Resolve the Vault entry inside the application, seal it for that Runner, and send the existing confidential fill command without exposing the key lookup, value, or encrypted transport payload to model-visible tool results. This retains the existing Runner fill behavior and keeps plaintext out of the Browser command envelope. It adds an authenticated public-key handoff and requires fencing replacement of the Runner between key discovery and dispatch.
- **B. Add a dedicated confidential fill operation to the Runner.** Carry the resolved value in a dedicated sensitive field over authenticated Runtime Control, with explicit exclusion from ordinary request records, diagnostics, and generic error handling. This avoids discovery of a process public key, but extends the Runner contract and places more of the Control serialization path inside the plaintext boundary.

**Recommendation (pending):** A. It keeps the established confidential Browser receiver and avoids adding another plaintext transport path. Key discovery failure or Runner replacement must not fall back to ordinary `text` or the shell. An uncertain fill still requires observation before any repeat. The internal CLI environment and file-intake paths still need bounded, value-free diagnostics and explicit synthetic-secret tests; they do not inherit protection from this Browser mechanism.

## D6. Reuse the Runner's encrypted Browser fill

- Status: Accepted on 2026-11-27.
- Requirements: [vault-261127/REQ-2](../requirements/vault-261127-agent-vault.md#req-2-explicitly-use-entries-in-a-tool-call) and [vault-261127/REQ-5](../requirements/vault-261127-agent-vault.md#req-5-keep-plaintext-out-of-normal-product-records).
- Decision: Obtain the recipient public key through authenticated Control for the admitted Runner generation. Seal the resolved Vault value within the application and dispatch the existing confidential fill to that generation. Keep the key lookup and Vault ciphertext internal. The Runner performs existing Browser target admission and decrypts only for the field input. Unavailable or stale recipient evidence fails closed without a shell or plaintext fallback.
- Rationale: The existing encrypted fill already provides the last-mile decryption and value-free error path. A dedicated plaintext Control operation would increase the number of components that handle the secret without changing the intended Browser effect.
- Consequences: The design must bind key discovery and dispatch to the same process lifetime, cover unsupported or replaced Runners, and preserve the existing observation-before-retry rule. The existing literal and externally supplied ciphertext flows remain unchanged.

## Feasibility follow-up: Runtime transport and request settlement

The following are design checks and candidates, not accepted decisions.

### Runtime transport

- **Observed:** [`process.start`](../../../python/apps/azents/src/azents/runtime/control_protocol/runner_operations.py) places the supplied environment in the operation payload. The normal Runner file read returns source bytes as Base64 in a reply event. [Runtime Control](../spec/flow/agent-runtime-control.md#coordination-store) appends request and reply events to generation- or request-scoped coordination streams, including on Redis. Omitting a value from model-visible tool output therefore does not keep raw values out of the ordinary Control stream.
- **Existing seams:** Runner registration carries authenticated capability/metadata evidence, and Control dispatch checks and atomically appends against the current connection generation. The dispatch service assigns request and operation identities before appending. The ordinary process path can rebind before append; an encrypted operation must pin recipient selection, sealing and append to the same admitted generation, not let existing rebind logic send a prepared envelope to a different Runner. See [registration](../../../python/apps/azents/src/azents/runtime/control_protocol/grpc/runner_server.py), [dispatch](../../../python/apps/azents/src/azents/runtime/control_protocol/service.py), and [reply fold and cancellation](../../../python/apps/azents/src/azents/runtime/control_protocol/runner_operations.py).
- **Operation design checks:** Use closed typed request/reply shapes and cryptographic context for protocol, direction, Runtime, Runner generation, requesting Session, operation identity and deadline. Keep transport private keys outside the deployment storage key, child environments and model-visible interfaces. In particular, do not share a decryption context with Browser `encrypted_text`: a Browser fill cannot be used to decrypt or consume a captured CLI envelope. Decode file content only in the originating app operation; a stale, mismatched, cancelled, or incomplete result cannot lead to a Vault write. The final write revalidates Agent execution authority. A lost app recipient or unknown dispatch does not cause replay or a new write.
- **Consumer design checks:** Compose the existing execution backend environment, then apply explicitly nominated ordinary names only for the launched process; keep Runner-owned names reserved and reject an invalid or reserved assignment before start, not by silently ignoring it. The existing backend can otherwise override operation-provided env values. File intake needs a single bounded read of an accessible regular-file descriptor (read up to limit plus one, reject oversize without truncating, no new scratch copy). Review filesystem access and cancellation against the [Runner file and process handlers](../../../python/apps/azents-runtime-runner/src/azents_runtime_runner/operations.py), [execution policy](../../../python/apps/azents-runtime-runner/src/azents_runtime_runner/execution.py), and [regular-file checks in transfer](../../../python/apps/azents-runtime-runner/src/azents_runtime_runner/transfer.py). Do not reuse the full transfer snapshot path merely to read a Vault value.
- **Checks:** Trace request and response serialization, errors, retry and generation changes, and both Coordination Store backends. Prove that synthetic CLI and file-import values are absent from serialized Control streams and ordinary product records while the nominated consumer receives the value. Confirm no private or symmetric key is exposed to Agent tools or inherited process environments, and no new plaintext fallback exists. This does not add output filtering or change ordinary environment or file operations.

### Request settlement and provider cleanup

- **Deep link and projection:** Use the existing authenticated Session route as the entry point, not a separate provider or Azents form page. An opaque request identifier carries no authority. Current chat authorization matches the exact Workspace, Agent and Session, including User Session owner isolation; Vault manager permission is a separate check. The general unauthenticated redirect preserves the query, but the Workspace membership error fallback can lose it; include expired sign-in in the deep-link test. Ordinary history is append-only and a detached page need not contain a later terminal event. Compare a value-free history anchor with independently refreshed request state against a separately merged request timeline feed. A terminal event alone is not sufficient. Retention can delete compacted history events regardless of model visibility, so prove an open card retains its placement across compaction. See [Session resource authority](../../../python/apps/azents/src/azents/repos/session_resource_authority.py), [chat resync](../spec/flow/chat-session-resync.md), and [compacted event retention](../../../python/apps/azents/src/azents/repos/compacted_event_retention.py).
- **Lifecycle fence:** Archive takes the active Agent fence before the ordered Session locks; Agent retirement takes the Agent write fence. Revalidate exact Session and Agent authority before locking the request and performing D4. Use elapsed database time after the write-lock wait, not transaction start time, to settle the deadline. No request may submit through an archived Session or retired Agent. Catalog Session request resources and Agent entry resources in the existing [Session lifecycle](../spec/execution/session-lifecycle.md) and [Agent deletion](../spec/domain/agent-deletion.md) boundaries. Distinguish operator stop and child Session inbox rules from human composer admission; never retarget a completion to a parent Session.
- **Expiry and recovery:** A persisted deadline makes link admission fail immediately at expiry, regardless of any later reconciliation. The existing [periodic scheduler](../../../python/apps/azents/src/azents/scheduler/registry.py) can advance bounded due rows even with no visitor. Its claims schedule handler runs, not individual Vault edits; any durable per-request delivery intent needs its own retry evidence. Neither a browser timer nor a bare post-commit best-effort callback can provide visitor-independent expiry reconciliation with crash recovery.
- **Exact provider identity and authority:** Discord update needs the stored channel and message ID and Slack update needs the stored channel and timestamp, under the exact verified provider connection. The original Session is not a destination-binding lookup. The current Channel Work mutation gate is tied to its source Session; reuse the lower-level provider APIs without invoking that state machine. Explicitly replace all link-bearing message components when settling. No edit through a revoked route, alternate destination, or inherited cleanup privilege. The destination may be revoked independently of the source Session, and source purge can run immediately; do not imply retries survive purge without a separately authorized retention boundary. See [Provider delivery](../spec/flow/external-channel-delivery.md), [Discord adapter](../../../python/apps/azents/src/azents/services/external_channel/discord_delivery.py), and [Slack adapter](../../../python/apps/azents/src/azents/services/external_channel/slack_events.py).
- **Ambiguity:** Do not replay an unknown create; the Discord nonce covers only live duplicate attempts and the existing Slack adapter offers no equivalent durable idempotency. A post with a live link can lose its receipt, leaving no known identity to edit. Compare a one-call create against posting a link-free message first, persisting its receipt, then enabling the input link at that exact message. The latter trades an extra provider request for never deliberately publishing a link without recording where to clean it up; it still needs ordering and reconciliation after an ambiguous link enable. Link invalidation and D4 do not depend on any provider outcome.
- **Scope:** Success wake and the fixed deadline are required. Archive and restore change the existing Session access gate, not the request's deadline or status; a terminal request cannot reopen. Expiration or cancellation wake, a designated submitter, and explicit file overwrite are not assumed extensions. No extra Run pause, new human-message requirement, or special channel waiting mode is needed.

### Primary verification cases

Exercise a successful multi-field submission from the actual web chat, connected-provider link resolution and terminal status, called-only CLI delivery, Browser fill on the admitted Runner, and file registration by an Agent without an initiating user. Use existing Browser and provider fixtures with synthetic values. Cover races, unsupported Runner, expired or unauthorized links, and serialization/diagnostics in narrower deterministic tests where possible. Prove that synthetic values do not appear in the model request, transcript, feature diagnostics, or the Vault-specific Control envelopes. A passing document validator is not implementation or E2E evidence.

## Decision brief: confidential CLI delivery and file intake

**Question:** Keep Vault traffic on the existing admitted Runtime operation path as ciphertext, or move Vault bodies to a separately routed, non-retaining channel?

- **A. Send typed encrypted payloads on the existing Control streams.** Keep the current admission, exact Runner generation, operation deadline, reply and cancellation path. Use the authenticated registration seam for a dedicated Runtime transport recipient, and a per-operation application recipient for file intake. The application and Runner authenticate and bind the protected content to the operation; plaintext exists only at the endpoints. This adds capability negotiation and typed payloads to the current protocol. The existing stream retention policy still applies to ciphertext and routing evidence, not to the value or private keys. An old or replaced Runner cannot use a prepared envelope; the feature fails closed.
- **B. Send Vault bodies on a non-retaining authenticated side channel.** Keep routing intent on Control but use a separate bounded body exchange at the exact Control owner and Runner. Do not retain even ciphertext bodies in the ordinary streams. This requires extending or adding a body route from the originating application to the exact authorized Runner in both directions, with independent claim, deadline, cancellation, restart and overload handling. The existing Runner transfer body RPCs provide a streaming precedent, not this end-to-end Vault route; the complete-file direct-object feature would persist a copy and is not a Vault substitute.

For B, Redis carries only operation identity, routing, deadline, and value-free state. The originating application uses a short-lived live gRPC exchange through the Control replica that owns the authenticated Runner connection, with recipient-encrypted bodies held only in bounded transport memory. The app sends the sealed CLI environment to that Runner, or the Runner returns a sealed bounded file read to the app for the ordinary encrypted Vault write. Bind the exchange to one admitted operation and Runner generation; do not spool to Redis, an object store, or a temporary file. If the exchange is interrupted before body acceptance, fail without proceeding. If process start may already have occurred, report an unknown outcome without automatic replay. Incomplete file intake does not write an entry. The Runtime Web byte path is a precedent for owner-routed live streams; the existing transfer RPC implementations read or publish storage objects and cannot be used unchanged as the Vault body path.

**Key custody for both candidates (accepted separately in D7):** D2's long-lived deployment key is application-side storage authority only and must be recoverable separately from the database backup. For CLI, the proposed recipient is a dedicated Runner keypair generated in the Runner process, separate from the Browser fill key. Advertise only its public key through authenticated registration and bind its use to the admitted generation. For file intake, the originating application creates a fresh recipient keypair per operation and releases the private key when the operation settles or times out. Transport private keys are not deployment secrets, are not backed up, and remain in recipient process memory; no private key is sent through Redis or a child environment. Runner replacement invalidates dispatch to the old generation; a new process has a new key. This is not a retroactive confidentiality guarantee: under A, an attacker who obtains a recipient private key and its retained ciphertext could decrypt that ciphertext. B removes the stored transport copy, not exposure from a compromised endpoint while it handles the value.

**Recommendation (accepted in D8):** A under the confirmed plaintext boundary. It protects both directions and retains one admission and settlement path. B is the alternative if even retained transport ciphertext is unacceptable. Neither changes durable Vault entry encryption, the source file, or ordinary command and file operations. The existing Browser decision does not settle this bidirectional protocol; keep Browser's receiver and contract separate.

## D7. Keep CLI and file transport private keys at their recipients

- Status: Accepted on 2026-11-28 (KST). Transport retention remains undecided.
- Requirements: [vault-261127/REQ-2](../requirements/vault-261127-agent-vault.md#req-2-explicitly-use-entries-in-a-tool-call), [vault-261127/REQ-3](../requirements/vault-261127-agent-vault.md#req-3-register-a-value-from-an-agent-runtime-file), and [vault-261127/REQ-5](../requirements/vault-261127-agent-vault.md#req-5-keep-plaintext-out-of-normal-product-records).
- Decision: For CLI delivery, generate a dedicated recipient keypair in the Runner process, separate from Browser fill, and associate its public key with the authenticated, admitted Runner generation. A new Runner process generates a new keypair. For file intake, the originating application generates a fresh recipient keypair for each operation and releases its private key when that operation settles or times out. Public-key exchange is authenticated and scoped to the admitted operation or generation. Keep transport private keys only in their recipient processes, out of persistent storage, backups, model context, and command environments. D2 continues to govern database encryption and D6 continues to govern Browser fill.
- Rationale: Recipient-specific keys separate the two directions and the Browser input context without provisioning another long-lived deployment secret or sharing the storage key with Runner or Control.
- Consequences: Stale, unsupported, or lost recipients fail closed. The design must test generation replacement, mismatched operations, and absence of private keys in transport and diagnostics. Key custody does not select how ciphertext is carried or retained. A process-lifetime key is not a forward-secrecy guarantee for ciphertext captured during that process lifetime.

## Decision brief: publish the provider link before or after recording message identity

The existing Discord and Slack adapters can update a known message, but neither guarantees recovery of its identity when an initial create succeeds and its receipt is lost. In particular, Discord's live nonce fence is not a durable recovery key, and the current Slack adapter does not replay an uncertain create. D4 keeps submission and the original Session inbox authoritative independently of these failures. D5 still requires the exact authorized channel and current provider authority for each effect.

- **A. Post the actionable message once.** The first and only create includes the link. Persist the confirmed provider receipt and settle the same message by replacing the link with a terminal status. The notification is actionable immediately and requires only one call to publish. If the provider created it but Azents never obtained or committed its identity, the stale link can remain in the channel after the request closes; the server still denies submission. Do not replay that create, infer ownership of another message, or change the destination.
- **B. Post without the link, record the receipt, then add the link by editing that message.** A lost or uncommitted create receipt can leave an inert status message, but Azents never knowingly publishes a live link without retaining its exact edit target first. A successful publication requires an extra provider call, and a user can see a message before it is actionable. Link enable may fail or have an unknown outcome; any later terminal reconciliation still has the exact target. Serialize application dispatch of link-enable and terminal writes and reconcile an ambiguous in-flight enable after terminal state. Provider-side ordering and actual link removal still require verification.

For either candidate, the same provider message must be targeted with the original installation/author and delivery-channel evidence. The proposed terminal recovery is a durable, bounded scheduler reconciliation of due messages with known identity; it may repeat the same link-free terminal update after a transient error or an unknown update outcome, never re-create a message. Lost provider authority, permanent failure, or source purge ends the retry path without weakening server-side closure. This introduces no detached retention beyond source purge and no retry of an unknown create. Distinguish initial delivery from terminal update recovery when validating this proposal.

**Recommendation at briefing (A selected in D9):** B if a live link without a recorded cleanup target is unacceptable. It addresses a create-receipt failure that even durable terminal retries cannot repair. A is the simpler option if that stale-link exception is acceptable. Neither option promises to remove a link after provider access has been revoked.

## D9. Publish the actionable provider message once

- Status: Accepted on 2026-11-28 (KST).
- Requirements: [vault-261127/REQ-4](../requirements/vault-261127-agent-vault.md#req-4-collect-multiple-values-in-azents-and-close-the-request).
- Decision: Include the link in the initial and only create at the exact authorized destination in D5. Retain the confirmed provider message identity and use it for the terminal edit. Do not stage a link-free message, replay an uncertain create, search for a replacement message, or fall back to another destination.
- Rationale: The link is actionable as soon as the first message appears. The normal path needs one publish call and no intermediate message state; the two-step alternative adds a provider call and a new edit race to address a lost-receipt edge case.
- Consequences: If the provider creates a message but its identity is unavailable, the visible link may remain in that message. The request's server-side deadline, completion, and authorization still prevent invalid submission. The initial publication decision does not govern retries of the terminal edit on a known message.

### Derived terminal settlement after D9

REQ-4 requires terminal updates and explicitly allows provider update failure; D4 makes the request independent of that effect, D5 restricts its authority, and D9 fixes its target. Retain the existing one-attempt provider effect semantics and use the existing scheduler and request rows to make expiry and the edit eligible without a visitor. An indexed, bounded pass claims the edit in PostgreSQL and performs it after commit. A known receipt that arrives after closure is eligible for the same terminal pass. The scheduler can revisit unclaimed rows after a restart; a crash after a claim or a failed edit may leave a dead link visible. A generic outbox, detached tombstone, or lease-based retry could strengthen delivery guarantees, but is neither required nor part of the requested minimal provider scope.
