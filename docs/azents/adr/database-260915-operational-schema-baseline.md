# Operational Schema Baseline Decision

- Snapshot: `database-260915`
- Document reference: `database-260915/ADR`
- Requirements: [database-260915/REQ](../requirements/database-260915-operational-schema-baseline.md)

## Context

The migration graph upgrades a fresh database to revision `097a97177350`, but the
result differs from both production and current SQLAlchemy metadata. Read-only
inspection confirmed that the production database at the same revision already
matches the deployed models and that the drift originates in the fresh baseline.

## Decisions

### database-260915/ADR-D1. Replace the graph with one current-head baseline

Replace the intermediate revision graph with one baseline whose revision ID remains
`097a97177350` and whose parent is `None`.

This preserves the revision already recorded by production, avoids replaying
obsolete transitions on empty databases, and makes the deployable graph represent
the current schema directly.

Rejected alternatives:

- Add another revision after `097a97177350`: existing production would require a DDL
  rollout even though it already has the desired schema.
- Repair the September 10 baseline and retain every later transition: this preserves
  transition complexity that has no remaining deployment consumer.

Risks:

- A database behind `097a97177350` cannot upgrade through removed ancestors and must
  first use a release that still contains that history.
- A production-only accidental schema object could enter the baseline if schema
  capture is not checked against SQLAlchemy metadata.

### database-260915/ADR-D2. Use production schema plus model agreement as authority

Use the read-only public-schema dump from the production deployment running the
same application revision as the physical schema authority, and require
`alembic check` to prove that it also agrees with SQLAlchemy metadata.

Production data is not an authority for migration contents. Only deterministic
code-owned singleton seeds are retained.

Rejected alternatives:

- Use SQLAlchemy `create_all` as the complete authority: it does not represent every
  PostgreSQL-specific function, trigger, partial index, or constraint.
- Use the current fresh migration output: it is the state proven to be stale.

### database-260915/ADR-D3. Make model-definition drift a required migration test

Run pytest-alembic's model-definition-versus-DDL invariant in the PostgreSQL
migration suite so CI rejects any new operations after a fresh upgrade.

This keeps the drift check in the same isolated database lifecycle as the existing
single-head and upgrade checks.

### database-260915/ADR-D4. Preserve historical FK timing and normalize it in model comparison

Preserve production foreign-key deferrability in the physical baseline and schema
fingerprint. Before Alembic's structural foreign-key comparison, normalize only the
reflected `deferrable` and `initially` options when the local and remote columns,
referenced table, match mode, update action, and delete action otherwise match.

The current models do not declare the historical timing option on most foreign
keys. Treating that option as an autogenerated model change would require hundreds
of declarations without changing application behavior. The schema fingerprint
remains authoritative for preserving the physical production property.

Rejected alternatives:

- Strip deferrability from the baseline: fresh databases would no longer match
  production transaction behavior.
- Add the option to every historical model foreign key: this creates broad
  repetitive model churn for a physical property already pinned by the baseline.

Risk:

- A future intended deferrability change must update the physical baseline or a
  forward migration and the schema fingerprint explicitly; `alembic check` does not
  infer this option from model declarations.

## Consequences

- Fresh installs receive one schema baseline equivalent to production.
- Existing production remains at the same revision and executes no migration.
- Historical transition-specific migration tests and stale migration code paths are
  removed or replaced.
- Future schema changes start from `097a97177350` as ordinary forward revisions.
- Alembic continues comparing foreign-key structure and actions but leaves the
  historical deferrability property under schema-fingerprint authority.
